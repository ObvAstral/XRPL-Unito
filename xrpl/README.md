# Payments, Escrow and 2-of-3 Vault Module · XRPL Testnet (v2)

Requires Node.js `>= 22.13.0`. From the repository root:

```sh
npm --prefix xrpl ci
npm --prefix xrpl test
```

## 1. Initial Setup of the Two Vaults and Testnet Check (`setup-wallets.ts`)

To create (or verify and resume on restart) the dev wallets, the two pre-funded 2-of-3 vaults on XRPL Testnet, and check whether the `NFTokenMintOffer` amendment is active:

```sh
npm --prefix xrpl run setup:wallets
```

- Saves development private keys in `xrpl/.xrpl-local/dev-secrets.json` (`0600`, git-ignored).
- Saves and prints `xrpl/.xrpl-local/public-config.json` to `stdout` for **Person A** and **Person C**:
  - `participants`: classic addresses for `alice`, `bob`, `cadAuthority`, `billboardAuthority`, and `operator`.
  - `vaults.cad`: CAD vault address with `SignerQuorum: 2`, signers `[alice, bob, cadAuthority]` (`SignerWeight: 1`), and `masterDisabled: true` (`asfDisableMaster`).
  - `vaults.billboard`: Billboard vault address with `SignerQuorum: 2`, signers `[alice, bob, billboardAuthority]` (`SignerWeight: 1`), and `masterDisabled: true`.
  - `capabilities.nftokenMintOfferEnabled`: validated result on the Testnet ledger `Amendments` object.
- If some addresses were already generated by Person A, pass them with `--participants <file.json>`. A second run on ready vaults sends no new transactions.

## 2. Contracts and APIs of `xrpl/escrow` for Person A and Person C

Entry point: `xrpl/escrow/index.ts` (shared types in `xrpl/shared/escrow-order.ts` and `xrpl/shared/signer.ts`).

- **Integer amount split (`splitRentalAmount(grossDrops, feeBps)`):**
  - Computes `feeDrops = floor(grossDrops * feeBps / 10000)` and `netDrops = grossDrops - feeDrops` in integer drops (e.g. `10000000` drops at `1000` bps = `1000000` to the authority + `9000000` net escrow).
- **Time-locked deposit per order (`EscrowService.deposit(order, bobSigner)`):**
  - Verifies on-ledger that the vault has the 3 expected signers and master key disabled, then submits `EscrowCreate` from `bob` to `order.vault` with `FinishAfter = endAt`, without `Condition` and without `CancelAfter`. Returns hash, state, and `escrowObjectId`.
- **Shared-snapshot verification (`EscrowLedger.verifyEscrowAt(order, snapshot)`):**
  - Called on the same `ValidatedLedger` used for `account_nfts`. Distinguishes `'missing'`, `'pending'`, `'mismatch'`, `'locked'` (funded rental), `'releasable'` ("releasable"), and `'credited_to_vault'` ("credited to vault"). Throws `LedgerUnavailable` (`503`) if the node does not provide a recent validated snapshot.
- **Release at maturity (`EscrowService.releaseToVault(order, createHash, operatorSigner)`):**
  - Once ledger close time passes `FinishAfter`, submits `EscrowFinish` from the operator account and returns the vault credit receipt.
- **2-of-3 multisig settlement (`prepareVaultPayout` + `addVaultSignature` or `settleVault`):**
  - Prepares `Payment` once with `SigningPubKey: ""` and `client.autofill(tx, 2)` (`Fee >= 3x`). Exposes `phase: 'awaiting_signatures'` ("awaiting signatures") until two valid signatures matching `VaultResolutionMode` (`'ordinary'`, `'arbitration_alice'`, `'arbitration_bob'`, `'inadmissible_refund'`) arrive, then combines blobs with `xrpl.multisign`, records the hash before `submit`, exposes `'awaiting_ledger'` ("awaiting ledger"), and checks `delivered_amount === netDrops` (e.g., all 9 XRP to the beneficiary).
- **Fee refund for interrupted checkout (`EscrowService.refundFee(order, acceptOfferHash, authoritySigner)`):**
  - After `checkoutDeadline`, first reconciles any `pending` deposits, checks for any active Bob escrows, verifies in validated `NFTokenAcceptOffer` metadata that the fee was truly credited to the authority, and sends at most one `Payment` of `feeDrops` to Bob.
- **Reconciliation and vault reservation release (`EscrowService.reconcileOrder(orderId)`):**
  - Reconciles all attempts for an order in `AttemptStore` (`escrow-attempts.sqlite`) and reports via `canReleaseVault` when the SQLite backend may reassign the vault to a new order.

## Rental v2 · Wallets, Agreements and NFTs

Build with `npm --prefix xrpl run build`. Run the CLI with
`node xrpl/dist/agreement/rental-cli.js <command>`. In the table below, `rental`
refers to this command. JSON responses are printed to stdout and confirmation
prompts appear in the terminal. To sign, review the terms and type `YES` (or `SI`).

| Step | Commands |
| --- | --- |
| Prepare identities | `rental wallet-create alice`, `rental wallet-create bob`, `rental wallet-create cad`, `rental wallet-create comune`. Retrieve an existing address with `rental wallet-address <role>` and fund dev addresses via the [Testnet faucet](https://xrpl.org/resources/dev-tools/xrp-faucets). |
| Test login | `rental login-issue localhost:3000 <sessionRef> > challenge.json`, `rental login-sign localhost:3000 challenge.json bob > response.json`, `rental login-consume localhost:3000 <sessionRef> response.json`. The final command returns the authenticated address once. |
| Issue title | `rental title-issue title.json cad > title-offer.json`, `rental title-accept title.json title-offer.json alice`. Use the validated ID in the catalog resource and proposal. |
| Sign terms | `rental proposal-sign proposal.json alice > signed-proposal.json`, `rental order-sign signed-proposal.json order.json bob > acceptance.json`. Copy `proposalHash` from Alice’s output into the order. In `agreement.json`, use `proposal` and `proof` from Alice’s output and put Bob’s entire output in `acceptance`. |
| Verify agreement | `rental rental-verify agreement.json resource.json`. The 10 XRP and 1,000 bps example yields `feeDrops: "1000000"` and `netDrops: "9000000"`. |
| Approve and deliver pass | `rental pass-issue agreement.json resource.json cad > pass-offer.json`, `rental pass-accept agreement.json resource.json pass-offer.json bob`. The validated receipt returns agreement and transaction hashes, ledger, pass and offer IDs, and credited fee. |
| Check the ledger | `rental mint-offer-mode` reads amendment status on a validated ledger. `rental pass-verify agreement.json resource.json <nftId> <ledgerHash>` returns `present`, `absent`, or `unavailable`. |

`title.json`, `proposal.json`, and `order.json` each contain an object with
the fields below. Use future UTC dates at second precision (e.g.
`2030-05-05T12:00:00Z`), with the deposit deadline at or before the rental start.

| File | Fields |
| --- | --- |
| `title.json` | `resourceId`, `issuer`, `alice`, `validFrom`, `validTo` |
| `resource.json` | All title fields, `titleNftId`, and the `vault` address provided by Person B |
| `proposal.json` | `protocol: "xrpl-unito:rental-proposal"`, `version: 2`, `network: "testnet"`, `splitRule: "floor-bps"`, `listingId`, `revision`, `resourceId`, `titleNftId`, `issuer`, `alice`, `startsAt`, `endsAt`, `priceDrops` (string), `feeBps` (integer) |
| `order.json` | `protocol: "xrpl-unito:rental-order"`, `version: 2`, `network: "testnet"`, `orderId`, `proposalHash`, `bob`, `vault`, `fundBy` |

Testnet seeds are separated per role with `0600` permissions. The CLI stores them
alongside local journals in `~/.local/state/xrpl-unito-rental`. You can choose
a private directory outside the repository with `XRPL_RENTAL_STATE_DIR`. If a
submission returns `pending`, repeat the same command with the same terms and
journal to reconcile its hash. `XRPL_TESTNET_NODE` selects `ripple` (default) or
`xrpl-labs`.

### Integration with Payments and Backend

- The backend uses `WalletLogin.issue(sessionRef)` and
  `WalletLogin.consume(id, sessionRef, proof)` in [wallet-login.ts](agreement/wallet-login.ts).
  The pending browser session must carry an opaque server-associated reference.
  After consumption, the backend opens its session for the returned address.
  Use the catalog configuration to verify title and vault with `verifyRental` in
  [rental.ts](agreement/rental.ts).
- Person B can use `LocalSigner.sign(tx)` and `LocalSigner.signPartial(tx)` from
  [wallet.ts](agreement/wallet.ts), or the `tx-sign` and `tx-sign-partial` CLI
  commands. For multisig, prepare the vault transaction once with `SigningPubKey: ""`,
  fee scaled for the number of signers, sequence, and last ledger sequence. Each
  participant approves and signs the exact same JSON. Combine blobs with `multisign`
  from `xrpl`.
- `verifyRentalTitle` and `verifyRentalPass` in [rental.ts](nft/rental.ts) use the
  ledger hash supplied by the backend. Use the same hash for escrow checks and
  enforce interval, calendar, and order status from the backend.
  `RentalNfts.revokePass` requires checking the deposit on the snapshot passed to
  its callback. Return `missing` only after reconciling submissions and confirming
  the deposit is absent. A validated revocation with `feeRefundDue: true` flags a
  pass revoked from Bob’s wallet. For the refund, Person B also uses the validated
  receipt of the paid fee.

## 3. Web Application, SQLite Backend and Demos (Person C)

Start the unified server (marketplace, access verification, CAD portal, and billboard player) in instant local simulation mode:

```sh
npm --prefix xrpl start
```

To connect to real XRPL Testnet after `npm --prefix xrpl run setup:wallets`:

```sh
XRPL_MODE=testnet npm --prefix xrpl start
```

### Served Web Surfaces

- `GET /` — Marketplace with wallet and resource selector. **XRP Movements** displays Alice, Bob, and vault balances plus the escrow-locked amount on a single validated ledger snapshot. Spendable balance excludes the XRPL reserve. Each order highlights the action available to the connected role.
- `GET /cad` — Demonstration CAD portal with the **Open demo project** button, Alice and Bob messages in `Europe/Rome` time, 2-second polling, and automatic closure at expiration.
- `GET /schermo/torino-01` — Fullscreen digital billboard player: blank white before publication and after expiration, `object-fit: cover` image during the authorized window.
